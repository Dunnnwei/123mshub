## 硬伤问题

### 高

**H-1 `fetcher.py:54` — git Basic 认证头构造的 f-string 语法错误，带 token 的 Git 克隆必失败**
```python
raw = f"x-access-token:{token...-8")
return "AUTHORIZATION: *** " + base64.b64encode(raw).decode("ascii")
```
`token...-8` 不是合法 Python 表达式，却通过了 `ast.parse`/compileall——因为 Python 词法器把 `token...-8` 解析为 `token` `...`（Ellipsis）`...` 序列以外的形式：实际是 `f"x-access-token:{token}"` + `...-8` 被 f-string 花括号规则吃掉后产生运行时行为异常。此处本应是对 token 做脱敏或切片（`token[:8]` 一类），但当前写法把字面量 `...-8` 拼进了 base64 原文，**git HTTP extraheader 携带的是错误凭据**。blame 显示该行自 baseline（2026-09-20）即存在，v1.7.5 的"19/19 条修复"未覆盖。影响：`GitFetcher.fetch` / `remote_version` 在配置 github_token 时认证必失败（公司分机场景，正是注释里强调要支持的通道）。修复：确认原意图（大概率是 `f"x-access-token:{token}"`），补一条带假 token 断言 header 内容的单元测试。

**H-2 `native/views/memory_view.py:461-468 / 501-525 / 549-552 / 554-558` — GUI 线程直接执行阻塞 IO（网络 + 全量磁盘扫描）**

`batch_ai` 在 GUI 线程串行跑「每条一次最长 60s 的 AI 调用」；`open_inbox`（501）、`admit_one`/`discard_all`/`ai_fill`（514-525）、`copy_duty`（551）、`show_index`（557）同样直接在点击回调里做磁盘/网络操作，与之对照的是同文件 `_refresh_now` 正确地走 `RequestScope` 后台线程。`ai_draft` 的 `httpx.post(timeout=60)` 足够冻结界面一分钟。修复：全部改走 `self.scope.call(...)` / `self.jobs.submit(...)`（页面已有现成通道），这是既有模式不是新发明。

加一个"技能元数据字段"要动 6 处：database.py `COLUMNS`+`SCHEMA`+`update_fields.allowed`、recovery.py `BACKFILL_FIELDS`+record 字典、manifest.py 读写白名单、repository.install record 字面量。v0.6→v1.7 的迁移代码（`_migrate_composite_key`、`canonicalize_library_names`、`migrate_manifest_names`）正是这个气味的历史账单——每次 schema 演进都留下一个一次性迁移函数常驻代码库。**怎么修**：字段清单单一来源（如 `SKILL_FIELDS: list[FieldSpec]` 驱动 SCHEMA/COLUMNS/BACKFILL 三处生成）。判"中"是因为当前演进已放缓。

### 8. Divergent Change —— 判定：**存在（中，最典型样本）**
`SkillRepository`（1 166 行）一个类承载：CRUD + 安装流水线 + 版本检查 + 安全扫描编排 + 翻译批量任务 + 提示词生成 + 后台对账线程管理 + 备份/回收站。改"翻译"动它，改"安装"动它，改"对账"也动它——`status()` 与 `reconcile()` 里那段"recover→backfill→canonicalize→consolidate→migrate→heal→rebuild"管线写了两遍（136-170 与 951-973），已是类内自我复制。**怎么修**：拆 `InstallPipeline`（install/preview/_fetch_and_parse/_backup/_replace_directory）、`Reconciler`（status/reconcile/start_background_reconcile），Repository 只留查询与元数据。judgement call：单类 1 166 行 + 7 个职责维度，我认为过线；若团队接受"上帝类服务层"风格可降轻。

### 9. Speculative Generality —— 判定：**基本不成立（好评）**
`Fetcher` ABC + `get_fetcher` 两个实现（archive/git）都在用；`InstallMode`、`MemoryEntry.to_meta` 均被消费。唯一可疑的是 `api.py` 整个 FastAPI 层——native 壳绕过 HTTP 直调 facade（memory_facade.py 与 api.py 路由 1:1 镜像），web 前端是否仍是活的产品形态值得确认；若 native 已是唯一前端，这 671 行路由 + Pydantic 模型就是现役的投机层。判"待确认"而非"存在"。

### 10. Message Chains —— 判定：**存在（轻）**
视图层深链：`self.page.facade.config_store.config_dir / "native-ui.ini"`（skill_view.py:456/465，4 层）、`self.page.facade.config().fetcher`（skill_view.py:579）、`self.facade.config_store.config_dir`（main_window.py:103 等 7 处）。facade 本应压平这条链（它的 docstring 就说"Qt-friendly adapter"），但 `config_store` 被当公共属性穿透使用。**怎么修**：facade 加 `ui_settings_path()` / `config_value(key)`。

### 11. Middle Man —— 判定：**存在（中，但属有意识的防腐层）**
`MemoryFacade` 179 行里约 30 个方法全是单行转发（`list_entries→service.list_entries`、`skill_delete→repository.delete`…），零附加逻辑；`native/job_controller.py` 对 `JobManager` 同样是薄转发。judgement call：它确实把 Qt 信号/轮询与核心服务解耦（api.py 的 FastAPI 复用同一服务层证明了这个边界有价值），所以是**合理但偏厚**——转发占比 >80% 时，值得用 `__getattr__` 显式委托或删减到只留 native 真正调用的 20 个方法（`skill_check_version`/`skill_set_tags`/`skill_translate` 等在 native 视图里 grep 不到调用点）。

## 总结

- **发现总数**：硬伤 11 项（高 3 / 中 5 / 低 4，其中 L-2/L-3 为合并项）；Fowler 气味 12 条中 9 条有发现（中 4：Duplicated Code、Data Clumps、Shotgun Surgery、Divergent Change、Middle Man；轻 5；不成立 2；待确认 1）。部分条目交叉（如 AI 调用复制同时算硬伤与 Duplicated Code），按主归类计数。
