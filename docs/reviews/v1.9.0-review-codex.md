## 2. 发现明细

### P0-1：在线升级信任未签名 Release 元数据，资产 URL/文件名可导向任意写入

- 位置：src/mshub/native/upgrader.py:36-62, 82-92；src/mshub/native/views/settings_view.py:466-508
- 证据强度：实锤（代码路径；远端元数据被控制是利用前提）
- 问题描述：
  - fetch_latest_release 只检查 HTTP 状态和 JSON 可解析性，将 tag_name、browser_download_url、name、size 原样放入返回对象。
  - pick_asset 只按字符串包含 123mshub-native-、扩展名和大小挑选 zip；没有固定 GitHub 资产主机、版本清单、SHA-256、签名或包内版本校验。
  - _start_upgrade 将远端 asset["name"] 直接做 Path(tmp) / name（:500、:506-508）。资产名若包含绝对路径或 ..\，下载目标就可能离开 TemporaryDirectory；用户确认弹窗只展示 tag、体积和 release body，没有展示或校验最终 URL/文件名。
  - 下载完成后 apply_upgrade 会把包内文件直接覆盖到 Path(sys.executable).parent，没有校验发布者、摘要或签名。
- 推理依据：更新链是“远端 JSON → 资产 URL/文件名 → 下载 → 解压 → 安装目录覆盖”的连续信任链。TLS 能保护正常 GitHub 连接，但不能抵御被配置代理返回伪造 JSON、发布账号/Release 资产被替换、或发布链被入侵；没有独立完整性校验时，用户看不到可验证的内容来源。文件名没有 Path.name 约束时，路径解析还扩大了写入范围。
- 建议修法：
  1. 资产 URL 只允许预期 GitHub Release 主机和 HTTPS；对重定向后的最终主机再次校验。镜像默认不带凭据。
  2. 资产名只允许 Path(name).name 且匹配固定正则（如 123mshub-native-v<semver>-win64.zip），下载目标固定使用 tmp / "upgrade.zip"。
  3. 发布流程提供签名或随 Release 发布的 SHA-256 manifest，升级前校验摘要/签名；校验 zip 顶层目录、版本文件和必需资源后再安装。
  4. 将“检查更新”和“信任安装包”分开显示，向用户展示被校验的版本、资产名和摘要前缀；校验失败不得覆盖。

### P0-2：技能硬删除没有验证 local_dir 的仓库边界

- 位置：src/mshub/repository.py:902-920
- 证据强度：实锤（静态路径构造；需要本地索引被篡改/损坏或出现异常目录字段这一前提）
- 问题描述：target = root / item["local_dir"] 后，硬删除分支直接执行 shutil.rmtree(target)。绝对路径会令 Path 丢弃左侧 root；相对的 ..\ 片段也可能解析到仓库外。软删除分支同样把该路径交给 shutil.move，所以不是只有硬删除存在边界问题。
- 推理依据：local_dir 来自本地 SQLite 记录（:905、:908），不是由本次删除操作重新生成的安全目录名。正常安装流程会生成仓库内相对路径，但删除入口没有重新验证这一不变量。用户选择带恶意或损坏索引记录的技能并确认删除时，删除操作可作用于仓库外目录。
- 建议修法：
  1. 先对 root 与 target 做 resolve()，用 target.relative_to(root) 检查必须在仓库根内；失败即拒绝删除并记录错误。
  2. 拒绝绝对路径、空路径、.、..\ 和符号链接目录；删除前确认目标是预期技能目录。
  3. 给 local_dir 加数据库迁移/重建校验，启动或 reconcile 时把越界记录标为损坏而不是继续使用。

### P1-1：GitHub Token 随镜像请求发送，镜像配置改变后会泄露凭据

- 位置：src/mshub/native/upgrader.py:95-120
- 证据强度：实锤（静态 header 路径；是否为恶意镜像取决于用户配置或配置被篡改）
- 问题描述：candidates 先放入所有 mirror_url(url, prefix)，随后构造一个共用的 Authorization: Bearer <token> header，并对每个候选地址调用 client.stream("GET", candidate, headers=headers)。Token 会发送给每个配置镜像以及直连地址；镜像只需转发或记录请求即可看到 Token。
- 推理依据：镜像是可配置字符串，并非代码内固定 GitHub 域名。技能抓取链路也使用镜像，但在线升级把同一个 GitHub Token 复用到完整包下载；没有“镜像不携带凭据”的策略或设置页提示。
- 建议修法：镜像请求默认移除 Authorization；只有经过明确配置、证书/主机白名单和用户确认的私有镜像才携带其专用凭据。直连 GitHub 与镜像下载使用不同 header 构造函数，并在日志中只记录候选主机，不记录凭据。

### P1-2：逐文件覆盖没有事务性回滚，失败会留下混合版本或缺文件安装

- 位置：src/mshub/native/upgrader.py:161-180, 193-213
- 证据强度：实锤（静态控制流；真实锁/断电触发属于运行前提）
- 问题描述：apply_upgrade 解压后按 rglob 顺序逐个调用 _copy_over。成功复制的文件没有备份；后续 PermissionError、磁盘空间错误、杀毒软件锁定或进程中断会直接从函数退出。Windows 锁文件路径先把旧文件改名为 .mshub-old（:171-180），如果改名后第二次 copyfile 失败，旧文件已离开原位置而新文件尚未写入。finally 只删除临时解压目录（:212-213），不会恢复安装目录。
- 推理依据：写入顺序没有预备目录、版本切换点、旧版备份清单或失败回滚分支；cleanup_old 只会在下一次启动尝试删除残留，不能恢复旧文件。
- 建议修法：先在同一安装目录生成完整新 payload，做清单、版本和摘要验证；将旧目录整体原子改名为备份，再把新目录原子改名为当前目录，失败时按清单恢复。若必须逐文件更新，至少记录每次替换并在异常时反向恢复，且不要先删除唯一的旧副本。

### P1-3：列表刷新/排序后 Shift 锚点仍是旧行号，连选可能选错条目

- 位置：src/mshub/native/ui.py:147-171；src/mshub/native/views/memory_view.py:153-161；src/mshub/native/views/skill_view.py:184-197；src/mshub/native/views/skill_view.py:748-766
- 证据强度：实锤（静态状态机分析；可由“点锚点 → 刷新/排序 → Shift 点击”触发）
- 问题描述：ShiftRangeCheckMixin 只在普通点击时写入 self._shift_anchor = row，没有公开的刷新/重建失效操作。三个页面刷新时都会清空/重建复选框并重新分配行号，但没有重置 _shift_anchor。之后 Shift 点击仍按旧整数索引计算 low..high，会把新区间勾选，且状态栏会报告错误行号。
- 推理依据：记忆页在 :160-161 重建 _row_checks；技能页和安全页在 :191-197、:760-766 重建表格控件；这三处都没有清除锚点。异步刷新、筛选切换、表头排序和后台删除都会改变行到条目的映射。
- 建议修法：每次列表数据、过滤条件或排序变化前后将锚点置为 -1，或者保存稳定的复合键（name/library）而不是行号；重建后只有当该键仍存在时才恢复锚点。连选前再次确认锚点行属于当前列表。

### P1-4：v1.9.0 单一完整包与 README/启动错误提示仍有旧环境包指引

- 位置：README.md:140-145；src/mshub/native/app.py:87-94
- 证据强度：实锤（文档/代码文本直接矛盾）
- 问题描述：README 快速开始和“Windows 系统依赖”已经写明 v1.9.0 起只发布单一完整包，但 FAQ :144 仍要求用户“先运行独立环境包的一键安装器”。当打包程序缺失 PySide6 时，app.py:92-93 的 ImportError fallback 也仍提示“请到发布页重新下载环境包”。v1.9.0 构建脚本和 missing_environment_text 已明确没有单独环境包，这些旧文案会把首装/损坏用户导向不存在或不再推荐的操作。
- 建议修法：统一改成“重新下载 v1.9.0 起的单一完整包并覆盖解压”，只在历史版本说明中保留旧分包信息；源码运行的 pip install mshub[native] 提示与打包版缺文件提示分开。

### P1-5：zip 解压没有限制解压后总量，1GB 压缩上限仍可被 zip bomb 放大

- 位置：src/mshub/native/upgrader.py:32, 121-129, 143-158
- 证据强度：实锤（静态资源计数缺口；是否达到磁盘耗尽取决于压缩比和可用磁盘）
- 问题描述：下载阶段只限制传输字节数 MAX_PACKAGE_BYTES = 1GB，解压阶段逐成员直接 copyfileobj，没有使用 ZipInfo.file_size、成员数、累计未压缩字节数或剩余磁盘空间上限。一个远小于 1GB 的高压缩 zip 可以在 temp_root 解压时占满临时盘，阻塞或拖垮应用。
- 建议修法：在写入前检查每个成员的 file_size、路径长度和总未压缩大小，设置远低于磁盘容量的发布包上限；复制时按字节累计并在超限时中止；对目录/文件数量也设上限。

### P2-1：cleanup_old 递归删除安装目录下所有匹配后缀文件，作用域缺少专用残留目录

- 位置：src/mshub/native/upgrader.py:216-227
- 证据强度：推测（需要用户/第三方在安装目录放置同名后缀文件；正常 onedir 包通常不会有此类文件）
- 问题描述：启动时对整个安装目录执行 rglob("*" + OLD_SUFFIX)，对每个匹配文件直接 unlink。它没有记录“本次升级创建的残留清单”，也没有限制文件必须位于程序文件清单中；安装目录中用户手工放置的 .mshub-old 文件会被当作升级残留删除。目录匹配会失败并被静默忽略，因而还可能留下残留。
- 建议修法：把残留放入专用 .mshub-staging\old\ 或保存带版本/哈希的清单，只清理清单中的旧文件；对目录按预期类型处理并保留失败记录。
