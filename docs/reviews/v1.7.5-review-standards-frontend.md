- 审查基准：mattpocock code-review 技能 Standards 轴（Fowler 气味基线）+ 前端硬伤清单。

## 硬伤问题

### 高

**H1. 后端不可达时任务轮询永久空转（内存/资源泄漏性质）**
`web/src/jobStore.js:47-50`

```js
} catch {
  // 后端暂时不可达时继续轮询，直到没有进行中的任务
}
jobStore.timer = window.setTimeout(tick, 900)
```

`tick` 的退出条件（43-46 行 `if (!jobStore.runningCount) return`）只在 `api.jobs()` **成功**的分支里；一旦 fetch 抛错进入 catch，跳过退出判断，无条件 900ms 后再排一轮。后果：后端进程被杀后，前端每 900ms 发一次注定失败的请求，直到页面关闭——与注释意图（"直到没有进行中的任务"）相反。修复：catch 里同样检查 `jobStore.runningCount`，或引入连续失败计数后退避/停轮。

**H2. `api.js` 请求头合并被 `...options` 覆盖（潜在 bug，当前无调用方触发）**
`web/src/api.js:18-21`

```js
const response = await fetch(path, {
  headers: { 'Content-Type': 'application/json', ...(options.headers || {}) },
  ...options,
})
```

`...options` 在 `headers` 之后展开，若调用方传了 `options.headers`，会把前面合并好的整个 `headers` 对象覆盖掉，`Content-Type: application/json` 静默丢失。当前 128 行内没有调用方传自定义 headers，所以是潜伏雷而非现网 bug，但封装层留这种顺序错误迟早被踩。修复：把 `...options` 移到 `headers` 之前，或解构剔除。

### 中

**M1. `dismissed` 任务仍计入 runningCount，可致轮询停不掉**
`web/src/jobStore.js:32-33`

```js
jobStore.items = data.items.filter((job) => !dismissed.has(job.id))
jobStore.runningCount = data.items.filter((job) => job.status === 'running').length
```

`items` 过滤了 dismissed，`runningCount` 却用未过滤的 `data.items`。用户 dismiss 一个仍卡在 running 的任务后，面板空了但轮询永不停止（43 行退出条件永远不触发）。与 H1 同根因：退出条件依赖的数据口径不一致。

**M2. 所有 fetch 无超时/AbortController**
`web/src/api.js:17-33`。`request()` 裸 `fetch`，后端挂起（非拒绝）时 Promise 永远 pending。多数调用点有 `loading` 态兜底，但如 `selectSkill`（App.vue:240-252）这类"先开抽屉再取数"的路径会让抽屉永远停在 loading。修复：`AbortSignal.timeout(15000)` 起步。

**M3. `batchCheckVersion` 串行 await 无并发也无总数提示**
`web/src/App.vue:429-436`。循环里 `await api.checkVersion(...)` 逐个串行，N 个条目就是 N 个 RTT 且无任何进度反馈，用户在多选几十项时会面对一个"死住"的界面。同类问题在 `performBulkAiTopic`（MemoryView.vue:313-325，每条 3 个串行请求）更严重。修复：`Promise.allSettled` + 并发上限。

**M4. 键盘可达性缺口：可点击 `<article>` 无键盘支持**
- `web/src/components/SkillRow.vue:25` — `<article class="skill-row" ... @click="emit('select', skill)">` 无 `tabindex`/keydown，整行点击区键盘不可达（行内 skill-name 按钮 38 行可聚焦，部分缓解）。
- `web/src/components/SecurityView.vue:35,57` — `<article class="security-row" @click="...">` 同样问题。
- `web/src/components/MemoryView.vue:650-653` — 有 `role="button" tabindex="0" @keydown.enter`，但缺 `@keydown.space`（`role="button"` 的约定是 Enter+Space 都可激活），且未阻止 Space 默认滚动。

### 低

**L1. MemoryView 框选未排除右键** — `web/src/components/MemoryView.vue:215` 的 `selectionStart` 没有 App.vue:383 那样的 `event.button !== 0` 检查，右键拖拽也会拉出选择框。

**L2. `toastTimer`/`reconcileTimer` 清理不对称** — App.vue:151-154 清了 `reconcileTimer` 但没清 `toastTimer`（43 行声明）。App 是根组件实际不会卸载，影响为零，但同一块 `onUnmounted` 里清一个漏一个是坏习惯。

**L3. `SettingsView` 镜像地址硬编码进模板** — `SettingsView.vue:280` 把 `https://ghproxy.link/`、`https://ghfast.top/` 两个第三方镜像写死在模板里，这类服务时效性强，宜由后端配置下发。

**L4. `ImportModal` 关闭按钮恒可用绑定** — `ImportModal.vue:205` `:disabled="false"` 是死绑定，要么删掉，要么本意是 `:disabled="busy"`（与 197 行背景点击的 `!busy && close()` 不一致——背景可点关、按钮任何时候能点，行为分裂）。

## Fowler 气味发现

### Duplicated Code（最明显的气味）

1. **框选逻辑整段复制**：App.vue:382-402（`selectionStart/selectionMove/selectionEnd`）与 MemoryView.vue:215-257 是同一套 pointer 框选实现，连"8px 阈值"都一样，仅选择键不同（`data-skill-key` vs `data-memory-key`）。App 版在 pointermove 里做命中计算，MemoryView 版挪到 pointerup 里做——已经分化出两种行为，正走在"改一处忘另一处"的路上。应抽 composable（`useRubberBandSelection`）。
2. **AI 预设回填逻辑复制**：ScanModal.vue:32-36、40-51 与 SettingsView.vue:49-53、59-62 是同一段"按 base_url 匹配预设 / 应用预设"逻辑，含同一条正则 `replace(/\/$/, '')`；默认网关 `'https://api.openai.com/v1'` 与默认模型 `'gpt-4.1-mini'` 也各写两份。
3. **库名映射表两份**：DetailDrawer.vue:46-51（`LIBRARY_NAMES`）与 SkillRow.vue:7-12（`LIBRARY_SHORT`）各自维护 `github/skills/zcode-skills/workbuddy-skills` 的显示名，新增库要改两处（兼 Shotgun Surgery）。
4. **MemoryGraph 两个 watch 源列表重叠**：MemoryGraph.vue:587-589 与 592-605 把 `selectedTypes.user/project/reference/feedback` 四个 getter 各抄一遍，加一个类型要改三处（含 `typeColors`/`typeLabels`）。

### Primitive Obsession

5. **`skillKey` 字符串拼键当身份**：App.vue:78-80 `` `${skill.name}|${skill.library || ''}` `` 作为选择集 key 贯穿 selectedNames/refreshSkills/viewScanResult，还要在 213-216 行 `key.split('|')[0]` 反解。条目身份值得一个 `{name, library}` 值对象或独立 id。
6. **`confirmState.action` 把函数塞进响应式状态**：App.vue:88-95、310-317 等，`ConfirmModal` 靠 `@confirm="confirmState.action?.()"`（1022 行）回调。能工作，但状态里藏闭包让确认框无法序列化/测试，也让 MemoryView 要 emit 一个带函数字段的对象（MemoryView.vue:298-306）穿越组件边界。

### Shotgun Surgery / Repeated Switches

7. **`item_type === 'project'` 三元判断散布 10+ 处**：App.vue:258、302、583、605-606；SkillRow.vue:44、69-71；DetailDrawer.vue:149、302、315、433；AddSkillModal.vue:303、334、390。加第三种条目类型要扫遍全前端。同理 `security_status` 的 `safe/warning/unchecked` 字面量在 App.vue:102、142-143、SecurityView.vue:11-13、StatusBadge.vue:9-14 反复出现。建议收敛为 `skillKind.js` 的领域函数（`isProject(skill)`、`displayName(kind)`）。
8. **`(name, library = '')` 参数对成 Data Clump**：api.js:46、51、56、60-62、69-73 几乎每个技能接口都重复 `(name, library)` 签名与 `JSON.stringify({name, library})` 体。传一个 `skillRef` 对象即可消掉。

### Divergent Change

9. **App.vue 是上帝组件**：1035 行里同时装着主题切换（66-76）、locale watch（61-64）、技能 CRUD/批量操作（274-481）、任务完成分发（483-518）、框选（382-402）、确认框状态机（88-95）。加任何一个技能库功能都要改这个文件。`jobFinished`（483-518）按 `job.kind` 的 if 链也是典型 Repeated Switches，新任务类型要改这里。

### Mysterious Name

10. **SkillRow 的 `@menu` 事件实际是"切换安装模式"**：SkillRow.vue:21 声明 `'menu'`，107 行 `emit('menu', skill)`，App.vue:921 接 `@menu="requestModeChange"`。名字叫 menu，语义是 mode-change，读模板时会以为要弹菜单。
11. **`currentBusy`**（App.vue:704-706）——名字像通用忙碌态，实则是"这个 skill 是不是正在被操作的那个"。
12. **`raw`**（MemoryGraph.vue:45）——图谱数据 ref 叫 raw，`syncGraph(result)` 的参数又和 `raw.value = result` 脱节命名。

### Speculative Generality / 死代码

13. **`inboxAdmitted` 空函数**：MemoryView.vue:174-176 函数体只有一行注释，模板 567 行还挂着 `@admitted="inboxAdmitted"`——要么删监听，要么里面该做的事（比如局部更新 stats）漏写了。
14. **`nodeProgramClasses` 四类型全映射到同一个 `NodeCircleProgram`**：MemoryGraph.vue:96-101，配合 548 行 `defaultNodeType: 'circle'`，这张映射表是纯摆设（注释 549-552 解释了动机，但 `defaultNodeType` 已足够）。
15. **`existingNames` computed 直通**：MemoryView.vue:72 `computed(() => allNames.value)`，纯粹的 Middle Man，直接用 `allNames` 即可。
16. **`defineExpose({ refreshAll })` 无消费方**：MemoryView.vue:493-495，App.vue 通过事件而非 ref 与 MemoryView 通信，expose 是悬空 API。

### Feature Envy

17. **框选命中检测直接摸子组件 DOM**：App.vue:396-399 `event.currentTarget.querySelectorAll('.skill-row[data-skill-key]')` 依赖 SkillRow 根元素的 class 名和 dataset（SkillRow.vue:25 配合埋点），MemoryView.vue:242-252 同理。父子靠 DOM class 契约耦合，SkillRow 改根 class 名就静默坏掉。

### Middle Man / Refused Bequest / Message Chains

- 未发现值得修的 Middle Man（EmptyState、StatusBadge 这类薄组件是合理展示组件）与 Refused Bequest（无继承体系）。
- Message Chains 有一处擦边：App.vue:945 通过 `document.dispatchEvent(new CustomEvent('mshub:open-memory', ...))` 让 MemoryGraph 间接通知 MemoryView 打开条目（MemoryView.vue:76、84-86 监听）。用 document 当事件总线绕过了 Vue 的 props/emit 契约，属于"全局暗线"；当前只此一处尚可忍，但应在注释里立规矩防止扩散。

## 总结

- **硬伤**：高 2 / 中 4 / 低 4，共 10 项；Fowler 气味 17 项（其中 #13、#14、#15、#16 为死代码/摆设，#9、#10、#12 等为 judgement call，不影响运行）。
- **最严重 3 项**：
  1. **H1 jobStore 轮询在后端不可达时永久空转**（jobStore.js:47-50）——资源泄漏 + 与注释意图相反，必修。
  2. **H2 api.js 请求头合并顺序错误**（api.js:18-21）——封装层潜伏雷，一行顺序修复，必修。
  3. **D1 框选逻辑双份复制且行为已分化**（App.vue:382-402 / MemoryView.vue:215-257）——最典型可执行的重构机会，抽 composable 一次解决 Duplicated Code + Feature Envy 两处气味。
- **值得肯定**：MemoryGraph.vue 的生命周期管理（destroyed 标志 + loadSequence 竞态保护 + 全部资源 kill）是范本；自研 markdown.js 的"先转义再渲染"路线避免了 v-html 注入；api.js 的 422 detail 格式化体现了对真实错误形态的了解。整体没有安全级硬伤，问题集中在可维护性。
